Digital Signatures, Key Management & Network Security

Now we put everything together. Digital signatures give authentication and non-repudiation; key management solves "how do two strangers get keys?"; and real protocols — Kerberos, PGP, S/MIME, SSL/TLS, IPSec and IKE — use all of it to secure e-mail, the web and whole networks.

4.1 Digital signature concepts

You need: public/private keys (Unit III), hash functions (Unit III) and the security services of Unit I (authentication, integrity, non-repudiation).

What a digital signature is

A digital signature is a value computed from a message and the signer's private key. Anyone with the signer's public key can verify that (1) the message came from the signer and (2) it was not changed. Note the reversal compared with encryption: sign with your own private key, verify with your public key.
Signed software and OS updates, PDF/e-contracts, income-tax e-filing with a Digital Signature Certificate (DSC), Aadhaar eSign, SSL/TLS certificates, e-mail (PGP/S-MIME), blockchain transactions.
Signing the digest: public-key operations are slow, so in practice the signer hashes the message and signs only the digest: S = Signprivate(h(M)). The verifier recomputes h(M) and checks it against the signature.
Proves the key signed, not the person — a stolen private key allows forgery; needs certificates to bind keys to identities; offers no confidentiality on its own.

A signature does not hide the message. For secrecy, first sign, then encrypt the message and signature (e.g. with a session key, as PGP does).

4.2 Signature schemes and their uses

RSA digital signature

RSA run "backwards": Alice uses her private key d to sign and anyone uses (e, n) to verify. Sign: S = Md mod n      Verify: M′ = Se mod n; accept if M′ = M In practice M is replaced by h(M) (with padding, e.g. PKCS#1 / PSS).
Most SSL/TLS certificates, code signing (Windows Authenticode), PDF signatures.
Example (keys from Unit III): n = 187, e = 7, d = 23. Sign M = 19: S = 1923 mod 187 = 94. Verify: 947 mod 187 = 19 = M ✓.
Textbook RSA signatures are vulnerable to existential forgery (pick any S, compute M = Se) and to multiplicative attacks (S₁·S₂ signs M₁·M₂) — signing the hash with padding prevents both.

ElGamal digital signature

Based on the discrete logarithm. Same keys as ElGamal encryption: public (e₁, e₂, p), private d with e₂ = e₁d mod p.

Sign: choose random r with gcd(r, p − 1) = 1.
S₁ = e₁r mod p;   S₂ = (M − d·S₁) × r−1 mod (p − 1).

Verify: V₁ = e₁M mod p;   V₂ = e₂S₁ × S₁S₂ mod p. Accept if V₁ = V₂.

Basis of DSA and Schnorr; used in GnuPG.
Example: p = 11, e₁ = 2, d = 3 → e₂ = 8. M = 5, r = 3 (r−1 mod 10 = 7). S₁ = 2³ mod 11 = 8; S₂ = (5 − 3·8) × 7 mod 10 = (−19)(7) = −133 ≡ 7. Signature (8, 7).
Verify: V₁ = 2⁵ mod 11 = 10; V₂ = 8⁸ × 8⁷ = 815 mod 11 = 10. V₁ = V₂ ✓.
r must be secret, random and never reused — reuse reveals the private key d. Signatures are twice the size of p.

Schnorr digital signature

A variant of ElGamal (Claus Schnorr, 1989) that works in a small subgroup of order q (≈ 160–256 bits) of ℤp*, making signatures much shorter. Signing: S₁ = h(M ‖ e₁r mod p), S₂ = r + d·S₁ mod q.
Bitcoin Taproot (2021) uses Schnorr signatures; EdDSA is a close relative.
Verification recomputes e₁S₂ × e₂−S₁ and checks the hash.
Was patented until 2008, which delayed its adoption.

Digital Signature Standard (DSS / DSA)

Adopted by NIST in 1994 (FIPS 186). Combines ElGamal and Schnorr ideas. Keys: primes q (160–256 bits) and p (1024–3072 bits) with q | (p − 1); e₁ = e₀(p−1)/q mod p (element of order q); private d; public e₂ = e₁d mod p.

Sign (random r, 0 < r < q): S₁ = (e₁r mod p) mod q;   S₂ = (h(M) + d·S₁) × r−1 mod q.

Verify: w = S₂−1 mod q; u₁ = h(M)·w mod q; u₂ = S₁·w mod q; V = (e₁u₁ × e₂u₂ mod p) mod q. Accept if V = S₁.

US government documents, older SSH and PGP keys; ECDSA (the elliptic-curve version) is used by Bitcoin, Ethereum, TLS certificates and Aadhaar-linked systems.
Tiny example: q = 11, p = 23, e₁ = 4 (order 11), d = 3 → e₂ = 4³ mod 23 = 18. h(M) = 7, r = 5 (r−1 = 9). S₁ = (4⁵ mod 23) mod 11 = 12 mod 11 = 1; S₂ = (7 + 3·1)·9 mod 11 = 90 mod 11 = 2.
Verify: w = 2−1 mod 11 = 6; u₁ = 7·6 mod 11 = 9; u₂ = 1·6 = 6; V = (4⁹ × 18⁶ mod 23) mod 11 = (13 × 8 mod 23) mod 11 = 12 mod 11 = 1 = S₁ ✓.
Signature only (no encryption); needs a high-quality random r for each signature (the Sony PS3 hack exploited a fixed r in ECDSA). DSA was removed from FIPS 186-5 (2023) in favour of ECDSA/EdDSA.

Time-stamped signatures include a trusted timestamp to stop replay. Blind signatures (Chaum) let a bank sign a coin without seeing it — used in e-cash and anonymous voting. Undeniable signatures can only be verified with the signer's cooperation.

4.3 Key distribution methods (symmetric keys)

Key Distribution Center (KDC)

With n users, pairwise secret keys need n(n − 1)/2 keys (1 million users → 5 × 1011 keys). Instead, every user shares one long-term secret key with a trusted KDC. When Alice wants to talk to Bob, the KDC creates a fresh session key KAB and delivers it to both, encrypted under their long-term keys.
Kerberos (Windows Active Directory logins, university/corporate networks), GSM authentication centres.
  • Flat multiple KDCs: the world is divided into domains, each with a KDC; for cross-domain talks the KDCs cooperate.
  • Hierarchical multiple KDCs: local KDCs → national → international, like a tree.
  • Session keys: valid for one session only — limits damage if one is exposed.
The KDC is a single point of failure and a high-value target (it knows everyone's keys); it must be online and trusted.

Needham–Schroeder protocol

The foundation of many KDC protocols (1978). Uses nonces (random numbers used once) for freshness. Five messages; KA, KB are the users' keys shared with the KDC.
Ancestor of Kerberos.
  1. Alice → KDC: RA, Alice, Bob
  2. KDC → Alice: KA[ RA, Bob, KAB, Ticket ], where Ticket = KB[ Alice, KAB ]
  3. Alice → Bob: Ticket
  4. Bob → Alice: KAB[ RB ] (challenge)
  5. Alice → Bob: KAB[ RB − 1 ] (proves she holds KAB)
If an old session key KAB is compromised, Eve can replay the old ticket (step 3) to Bob — fixed in Kerberos by adding timestamps.

Otway–Rees protocol

An alternative with four messages in which Bob contacts the KDC on behalf of both, using a common nonce R plus individual nonces.
Shows another way to bind session keys to a particular run.
  1. Alice → Bob: R, Alice, Bob, KA[RA, R, Alice, Bob]
  2. Bob → KDC: the same plus KB[RB, R, Alice, Bob]
  3. KDC → Bob: R, KA[RA, KAB], KB[RB, KAB]
  4. Bob → Alice: R, KA[RA, KAB]
Alice does not confirm that Bob actually received the key.

4.4 Symmetric-key agreement: Diffie–Hellman

Diffie–Hellman key exchange

Two parties create a shared secret over a public channel without any KDC and without having met. Published by Whitfield Diffie and Martin Hellman in 1976 — the paper that started public-key cryptography. Security relies on the discrete logarithm problem.
TLS (ECDHE in every HTTPS connection today), SSH, IPSec IKE, Signal/WhatsApp (X3DH), VPNs.

Public: a large prime p and a primitive root g.

  1. Alice picks secret x, sends R₁ = gx mod p.
  2. Bob picks secret y, sends R₂ = gy mod p.
  3. Alice computes K = R₂x mod p; Bob computes K = R₁y mod p.
K = (gy)x = (gx)y = gxy mod p

Example: p = 23, g = 7, x = 3, y = 6. R₁ = 7³ mod 23 = 21; R₂ = 7⁶ mod 23 = 4. Alice: K = 4³ mod 23 = 18. Bob: K = 21⁶ mod 23 = 18 ✓. Eve sees 23, 7, 21, 4 but must solve a discrete log to get x or y.

No authentication → man-in-the-middle attack: Eve intercepts R₁ and R₂, sends her own gz to each side, and ends up sharing one key with Alice and another with Bob, relaying (and reading) everything. Fix: authenticate the exchanged values (signatures/certificates) — the station-to-station protocol.

Station-to-station (STS) protocol

Diffie–Hellman plus certificates and signatures: each party signs the exchanged values (R₁, R₂) with its private key and sends its certificate, so Eve cannot substitute her own values.
The idea behind authenticated key exchange in IKE and TLS.
Alice → Bob: R₁. Bob → Alice: R₂, Bob's certificate, K[SignBob(R₁, R₂)]. Alice → Bob: Alice's certificate, K[SignAlice(R₁, R₂)].
Requires a PKI to issue and check certificates.

4.5 Public-key distribution, certificates and PKI

Public keys need not be secret, but they must be authentic — otherwise Eve publishes her key under Bob's name. Four approaches, from weakest to strongest:

1. Public announcement

Bob simply publishes his public key (website, e-mail signature, newspaper).
Early PGP users posting keys on personal pages.
No infrastructure needed.
Anyone can forge an announcement — no authenticity.

2. Trusted centre (public directory)

A trusted authority keeps a directory of public keys; users register in person or securely, and can look up others' keys.
Corporate address books with keys.
Directory is publicly readable; updates are authenticated.
The directory responses could be spoofed in transit; the centre is a bottleneck.

3. Controlled trusted centre

The centre signs each response (with a timestamp) using its own private key, so the requester knows the answer is genuine and fresh.
Online key servers.
User asks: "Bob's key?" → centre replies Signcentre(Bob's key, time).
The centre must be online for every request — heavy load.

4. Certification Authority (CA) and X.509 certificates

A CA verifies Bob's identity once and issues a certificate: a document binding Bob's identity to his public key, signed by the CA's private key. Bob can distribute the certificate himself; anyone who trusts the CA's public key can verify it offline.
Every HTTPS website (padlock in the browser), e-mail signing, code signing; in India, licensed CAs under the Controller of Certifying Authorities (CCA) issue DSCs.

Renewal: before expiry the CA issues a new certificate. Revocation: if a key is stolen or the owner leaves, the CA publishes it in a Certificate Revocation List (CRL) (or a smaller delta CRL of changes); modern browsers also use OCSP to ask about one certificate.

Everything depends on trusting CAs; a compromised CA (DigiNotar, 2011) can issue fake certificates for any site. Revocation checking is often slow or skipped.

Public-Key Infrastructure (PKI) and trust models

A PKI is the set of CAs, registration authorities, directories, policies and software that create, distribute, revoke and verify certificates. Trust models:

  • Hierarchical (tree) model: root CA certifies intermediate CAs, which certify users. Used by the web PKI. To verify Bob, follow the chain to a root you trust.
  • Mesh model: CAs cross-certify each other (peer-to-peer).
  • Web of trust: no CAs; users sign each other's keys (PGP, Section 4.7).

4.6 Kerberos

Kerberos authentication protocol

Kerberos (MIT, Project Athena; named after the three-headed dog guarding Hades) is an authentication protocol and KDC for a network. A user logs in once with a password and then gets tickets to use many services without sending the password again (single sign-on). It uses only symmetric cryptography plus timestamps.
Microsoft Windows Active Directory domain logins, university campus networks, Hadoop clusters, many UNIX/Linux enterprise systems.

Three servers:

  • Authentication Server (AS) — the KDC; knows every user's password-derived key; verifies the user and issues a ticket for the TGS.
  • Ticket-Granting Server (TGS) — issues tickets for specific real servers. (Separating AS and TGS means the password is used only once per login.)
  • Real server (Bob) — the service the user wants (file server, printer, mail).

Operation (six messages):

  1. Alice → AS: her identity (in plaintext).
  2. AS → Alice: a message encrypted with Alice's permanent key KA-AS (derived from her password) containing a session key KA-TGS and a ticket for the TGS (encrypted with KAS-TGS, which Alice cannot read). Alice's workstation asks for the password only now, to derive KA-AS — the password never travels.
  3. Alice → TGS: the TGS ticket, Bob's name, and a timestamp encrypted with KA-TGS (the authenticator — prevents replay).
  4. TGS → Alice: two items: KA-TGS[Bob, KA-B] for Alice and a ticket for Bob: KTGS-B[Alice, KA-B].
  5. Alice → Bob: Bob's ticket + timestamp encrypted with KA-B.
  6. Bob → Alice: KA-B[timestamp + 1] — confirms Bob's identity (mutual authentication).

To use another server, Alice repeats steps 3–6 with the same TGS ticket (valid for e.g. 8 hours).

Needs synchronised clocks (timestamps); the KDC is a single point of failure and must be highly secure; vulnerable to offline password-guessing on message 2 if passwords are weak; not designed for the open Internet across organisations.

A realm is the set of users and servers registered with one KDC. For cross-realm access, the TGSs of two realms share a key, and Alice obtains a ticket for the remote TGS from her local one.

4.7 Application-layer security: PGP and S/MIME

Alice's user agent (UA: Gmail app, Outlook) hands the mail to her message transfer agent (MTA, SMTP server), which sends it to Bob's mail server; Bob's UA fetches it with a message access agent (POP3/IMAP). E-mail is a one-way, store-and-forward activity: Alice and Bob are not online together, so there is no handshake to agree on algorithms or keys. Hence the secure-mail protocol must put the algorithm names, the encrypted session key and the signatures inside the message itself. E-mail also originally carried only 7-bit ASCII, so binary ciphertext must be encoded as text.

PGP (Pretty Good Privacy)

Created by Phil Zimmermann in 1991 and given away free; standardised as OpenPGP (RFC 4880). Provides privacy, integrity, authentication and compression for e-mail and files, using a web of trust instead of a CA hierarchy.
Journalists and activists, software release signing (Linux distributions sign packages with GPG), encrypted file storage, Git commit signing.

Scenarios (how a PGP message is built step by step):

  1. Plaintext — no security (just sent as is).
  2. Message integrity + authentication — Alice hashes the message and signs the digest with her private key; sends message + signature.
  3. Compression — the message (and signature) are compressed (ZIP) — after signing, before encrypting.
  4. Confidentiality with a one-time session key — Alice creates a random session key, encrypts the (signed, compressed) message with a symmetric cipher (IDEA/3DES/AES), and encrypts the session key with Bob's public key (RSA/ElGamal). Both are sent.
  5. Code conversion — the binary result is converted to ASCII text using Radix-64 (Base64): every 3 bytes → 4 printable characters.
  6. Segmentation — long messages are split to fit mail-size limits.

Bob reverses the steps: Radix-64 decode → decrypt session key with his private key → decrypt message → decompress → verify Alice's signature with her public key.

Hard for ordinary users (key management, trust decisions); metadata (subject line, sender, receiver) is not encrypted; no forward secrecy — a stolen private key decrypts all old mail.

PGP key rings, certificates and the web of trust

Each user keeps two key rings: a private key ring (own key pairs, private keys encrypted with a passphrase) and a public key ring (public keys of correspondents). Each key has a key ID (last 64 bits of the key). Instead of a CA, users sign each other's public keys — a PGP certificate. Trust is computed from these signatures: the web of trust.
Key-signing parties at conferences; Linux developers vouching for each other's keys.
For each introducer Alice assigns owner trust: none, partial or full. A key becomes legitimate (key legitimacy) if it is signed by one fully trusted introducer or by two partially trusted ones (configurable). Key revocation: the owner issues a revocation certificate signed with the key itself.
Trust decisions are manual and confusing; no central revocation; does not scale well.

S/MIME (Secure/Multipurpose Internet Mail Extensions)

S/MIME adds security to MIME, the standard that lets e-mail carry non-ASCII content (attachments, images, other languages). It uses X.509 certificates from CAs (not a web of trust) and the Cryptographic Message Syntax (CMS).
Built into Outlook, Apple Mail, Thunderbird; corporate and government e-mail where a CA hierarchy already exists.

MIME basics: five headers — MIME-Version, Content-Type, Content-Transfer-Encoding, Content-Id, Content-Description. Content types: text, multipart, message, image, video, audio, application. Transfer encodings: 7bit, 8bit, binary, Base64, quoted-printable.

CMS content types used by S/MIME:

  • Data — plain content.
  • Signed-data — content + digest signed with the sender's private key (+ certificates).
  • Enveloped-data — content encrypted with a random session key; the key is encrypted with each recipient's public key.
  • Digested-data — content + digest (integrity only).
  • Encrypted-data — encrypted content with a key managed separately.
  • Authenticated-data — content + MAC.

Algorithms: digests SHA-256 (MD5/SHA-1 historically); signatures RSA/DSA/ECDSA; content encryption AES or 3DES; key encryption RSA or Diffie–Hellman.

Needs every user to obtain a CA certificate; like PGP, headers are not protected; interoperability problems between clients.

4.8 Transport Layer Security: SSL and TLS

SSL / TLS overview

Secure Sockets Layer (SSL) was designed by Netscape (SSL 3.0, 1996). The IETF standardised it as Transport Layer Security (TLS) (TLS 1.0 = SSL 3.1, 1999; TLS 1.2, 2008; TLS 1.3, 2018). It sits between the application layer (HTTP) and TCP, giving a secure channel to any application: HTTPS = HTTP over TLS (port 443).
Every HTTPS website, secure e-mail transport (SMTPS, IMAPS), VPNs (OpenVPN), messaging apps, banking apps, APIs.
Services provided by SSL: fragmentation (blocks of ≤ 214 bytes), compression (optional), message integrity (MAC), confidentiality (symmetric encryption), framing (headers).
SSL 2.0/3.0 and TLS 1.0/1.1 are broken/deprecated (POODLE, BEAST); misconfigured servers, fake certificates and downgrade attacks remain risks. TLS protects data in transit only.

SSL architecture

Algorithms, cipher suites and parameter generation

The two sides negotiate a cipher suite — a combination of a key-exchange method, an encryption algorithm and a hash/MAC algorithm, e.g. SSL_RSA_WITH_3DES_EDE_CBC_SHA or TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256.
Lets old and new clients and servers find a common secure option.
  • Key-exchange algorithms: NULL, RSA (client encrypts the pre-master secret with the server's RSA key), anonymous DH, ephemeral DH (DHE, signed), fixed DH, Fortezza.
  • Encryption: NULL, RC4, RC2, DES, 3DES, IDEA, Fortezza (now AES-GCM, ChaCha20).
  • Hash for MAC: NULL, MD5, SHA-1 (now SHA-256/384).
  • Compression: optional (removed later due to CRIME attack).
  • Cryptographic parameter generation: client and server exchange random numbers; a pre-master secret is exchanged (via RSA or DH); both compute the 48-byte master secret = hash(pre-master secret, client random, server random); from it they derive the key material: client & server write MAC secrets, client & server write keys and IVs (six values).
Weak suites (export-grade, RC4, NULL) must be disabled on servers or downgrade attacks become possible.

An association between client and server created by the Handshake, holding the agreed cipher suite and master secret. Expensive to create — can be resumed.

A transport (TCP) relationship. One session can be shared by many connections, each with its own keys derived from the master secret.

The four protocols

1. Handshake protocol (four phases)

Negotiates the cipher suite, authenticates the server (and optionally the client) and establishes the secrets.
Runs at the start of every HTTPS connection (the padlock appears after it succeeds).
  1. Phase I — establishing security capabilities: ClientHello (highest version, client random, session ID, list of cipher suites, compression methods) → ServerHello (chosen version, server random, chosen suite and compression).
  2. Phase II — server key exchange and authentication: Certificate (server's X.509 chain), ServerKeyExchange (DH parameters, if needed), CertificateRequest (optional), ServerHelloDone.
  3. Phase III — client key exchange and authentication: Certificate (if requested), ClientKeyExchange (pre-master secret encrypted with the server's public key, or the client's DH value), CertificateVerify (proves the client owns its certificate).
  4. Phase IV — finalising: ChangeCipherSpec + Finished from the client, then ChangeCipherSpec + Finished from the server. "Finished" is the first message protected with the new keys and contains a hash of the whole handshake — detects tampering.
Two round trips before data can flow (TLS 1.3 reduces it to one).

2. ChangeCipherSpec protocol

A single one-byte message that tells the other side "from now on, use the newly negotiated (pending) parameters". It moves the pending state to the active state.
Sent by each side in Phase IV.
Message value 1; carried by the Record protocol.
Removed as a separate step in TLS 1.3.

3. Alert protocol

Reports errors and abnormal conditions. Each alert has a level (warning or fatal — fatal closes the connection) and a description.
close_notify (normal end), unexpected_message, bad_record_mac, decompression_failure, handshake_failure, no_certificate, bad_certificate, certificate_expired, certificate_revoked, illegal_parameter.
Two-byte message: level + description code.
Detailed alerts can leak information (padding-oracle attacks used error differences).

4. Record protocol

Carries messages from the upper layer (handshake, alert, CCS, application data), applying the agreed security.
Every byte of HTTPS traffic passes through it.
  1. Fragment data into blocks ≤ 214 bytes.
  2. Compress (optional).
  3. Add MAC computed with the write MAC secret (and a sequence number).
  4. Encrypt the compressed fragment + MAC with the write key.
  5. Add the SSL header: content type (8 bits), major/minor version (8 + 8), length (16).
MAC-then-encrypt order in SSL/TLS ≤ 1.2 enabled padding-oracle attacks (Lucky 13); TLS 1.3 uses AEAD (encryption + authentication together).

4.9 Network-layer security: IPSec

IP Security (IPSec)

A collection of IETF protocols that protect IP packets at the network layer. Because it works below TCP/UDP, it secures all traffic between two hosts or networks, transparently to applications.
Virtual Private Networks (VPNs) connecting branch offices over the Internet, remote-access VPNs for employees, securing routing protocols; mandatory support in IPv6.
Two modes × two security protocols, with keys negotiated by IKE, policies in the SPD and agreed parameters in Security Associations.
Complex to configure; problems with NAT (needs NAT-traversal over UDP 4500); per-packet overhead.

Two security protocols

Authentication Header (AH)

Provides source authentication and integrity of the whole packet (payload and the immutable parts of the IP header), but no confidentiality. IP protocol number 51.
When data may be read but must not be forged (some routing/government networks).
Fields: Next header (8 bits), Payload length (8), Reserved (16), Security Parameter Index (SPI) (32, identifies the SA), Sequence number (32, anti-replay), Authentication data (variable — an HMAC over the packet; mutable header fields like TTL are set to zero during calculation).
No encryption; breaks with NAT (because NAT changes the authenticated IP addresses).

Encapsulating Security Payload (ESP)

Provides confidentiality (encryption) plus source authentication and integrity. IP protocol number 50. Adds a header, a trailer and an authentication field.
Almost all VPNs use ESP (AH is rarely used now).
ESP header: SPI (32), Sequence number (32). ESP trailer: Padding (0–255 bytes), Pad length (8), Next header (8). Authentication data (variable). Encryption covers payload + trailer; authentication covers ESP header + payload + trailer (not the outer IP header).
In transport mode the IP header itself is not authenticated.

Security Association (SA), SAD and SPD

A Security Association is a one-way contract between two parties specifying the protocol (AH/ESP), algorithms, keys, sequence counters and lifetime. Two-way communication needs two SAs. An SA is identified by (SPI, destination address, protocol).
Every IPSec packet carries the SPI so the receiver can find the right SA.
Security Association Database (SAD): the table of active SAs (SPI, sequence counter, anti-replay window, AH/ESP info, lifetime, mode, path MTU). Security Policy Database (SPD): rules applied to every packet — discard, bypass (send without IPSec) or apply IPSec — selected by addresses, ports and protocol. Outbound: check SPD → find/create SA → process. Inbound: look up SA by SPI → verify → check SPD.
SAs must be created and refreshed securely — the job of IKE.

Internet Key Exchange (IKE)

IKE: creating SAs securely

IKE (RFC 2409; IKEv2 in RFC 7296) creates SAs for IPSec. It is built from three older protocols: Oakley (an improved Diffie–Hellman key exchange), SKEME (key exchange with public-key encryption for authentication and quick refresh) and ISAKMP (the message formats and framework — IKE packets are ISAKMP packets over UDP port 500).
Every IPSec VPN (Cisco, strongSwan, Windows, phones' built-in VPN clients).

Improvements over plain Diffie–Hellman:

  • Cookies against clogging (DoS) attacks — the responder does no expensive work until the initiator returns its cookie.
  • Nonces against replay attacks.
  • Authentication of the exchanged values against man-in-the-middle.

Two phases:

  1. Phase I — creates an ISAKMP (IKE) SA: a secure, authenticated channel between the two peers. Main mode (6 messages: negotiate SA → DH exchange + nonces → authenticate identities, which are protected) or aggressive mode (3 messages, faster, but identities sent in clear). Authentication methods: pre-shared key, digital signatures, public-key encryption (original and revised).
  2. Phase II — quick mode (3 messages), protected by the Phase I SA, creates the actual IPSec SAs (for AH/ESP) and can be repeated to refresh keys. Optional Perfect Forward Secrecy adds a fresh DH exchange.
IKEv1 is complex with many modes; aggressive mode with pre-shared keys allows offline guessing of the key. IKEv2 simplifies it (4 messages to set up).

4.10 Unit IV review and self-test

  • Signature = sign with private key, verify with public key; signs the digest; gives authentication, integrity, non-repudiation (not confidentiality).
  • RSA: S = Md, verify Se. ElGamal: S₁ = e₁r, S₂ = (M − dS₁)r−1 mod (p−1). DSA: S₁ = (e₁r mod p) mod q, S₂ = (h + dS₁)r−1 mod q.
  • KDC + session keys; Needham–Schroeder (5 msgs, nonces); Otway–Rees (4 msgs).
  • Diffie–Hellman K = gxy mod p; MITM unless authenticated (STS).
  • Public-key distribution: announcement → directory → controlled centre → CA certificates (X.509, CRL); PKI trust models.
  • Kerberos: AS, TGS, server; 6 messages; tickets + timestamps; single sign-on.
  • PGP: sign → compress → encrypt with session key (key encrypted with receiver's public key) → Radix-64; web of trust. S/MIME: MIME + CMS + X.509.
  • SSL: Handshake (4 phases), ChangeCipherSpec, Alert, Record (fragment → compress → MAC → encrypt → header). TLS: PRF, HMAC.
  • IPSec: transport vs tunnel; AH (integrity, no secrecy) vs ESP (both); SA/SAD/SPD; IKE Phase I (main/aggressive) and Phase II (quick).
